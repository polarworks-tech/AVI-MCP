# 設計方針

[REQUIREMENTS.md](REQUIREMENTS.md) で定義した機能群を、どういう考え方で・どの順番で
実装していくかの方針。「何を実現するか」ではなく「どう進めるか」を記す。

## 実装順序の基本方針

1. **読み取り系(カテゴリA)を優先して広げる** — 副作用がなく、間違っても壊れないため
2. **編集系(カテゴリB)はUndo可能な範囲から広げる** — AviUtl2の通常のUndo(Ctrl+Z)で
   元に戻せる操作は比較的安全に機能追加できる
3. **レンダリング系(カテゴリD)は読み取り系の次に広げる** — 実装はやや重いが、
   エージェントが操作結果を画像で確認できるようになる価値が大きい
4. **ファイルI/O・プロジェクト保存系(カテゴリF)は最後に、かつ個別に安全策を設計してから
   実装する** — 一度壊れたら編集データを失う可能性があり、Undoの効かない操作
   (ファイル上書き等)を含むため、「SDKにAPIがあるから呼べるようにする」だけでは
   実装として不十分。単に後回しにするだけでなく、着手時に専用の設計検討を行う。
5. **シーン操作(カテゴリE)・アプリケーション制御は原則やらない/最小限** —
   Undo非対応であることが明記されている、またはアプリ全体に影響するため

## リスクレベルの判断基準

| レベル | 基準 |
|---|---|
| 低 | 副作用がない(読み取りのみ)、または通常のUndoで即座に元に戻せる |
| 中 | Undo可能だが、複数オブジェクト・エフェクトに影響する、または非同期処理を伴う |
| 高 | Undo非対応、ファイルを上書きする、長時間ブロックする、アプリ全体に影響する |

リスクレベル「高」の機能は、実装前に「失敗時にどう安全側に倒すか」を
個別に設計してから着手する。

## オブジェクト識別の方針

- レイヤー・フレーム位置ではなく **`object_id`を主キーとする**。
  位置は編集操作のたびに変わるため、エージェントが連続して操作する場合に
  位置依存のAPIでは対象を取り違えるリスクがある。
- `object_id`はAviUtl2本体v2.1.11a以降の`get_object_id`に依存する
  (詳細: [SDK_NOTES.md](SDK_NOTES.md))。

## 安全性への基本姿勢

- 存在しない`object_id`や無効な引数を渡された場合は、クラッシュさせず
  明確なエラーメッセージを返すこと(ブリッジ・MCPサーバー双方の責務)。
- 破壊的操作(ファイル上書き、プロジェクト新規作成等)は、実装時点で
  「既定で無効化する」「確認フラグを必須にする」等のガードを検討する。
- 新しいSDK関数を使う前に、CHANGELOGで追加時期を確認し、
  本体バージョンとの対応を疑う習慣を持つ(詳細: [SDK_NOTES.md](SDK_NOTES.md))。

## MCPツール設計の原則

実装を通じて「SDK関数1つ = MCPツール1つ」という機械的な対応を続けた結果、
似た概念(オブジェクトの検索)が複数のツールに分散する等、エージェントから見た
使いやすさを損なう状態になった。以降は以下を原則とする。

- **ツールはSDK関数ではなくワークフロー単位で設計する**。複数のSDK関数が
  「本質的に同じ概念の異なる切り口」である場合(例: 位置検索/全件/選択中の
  オブジェクト取得は、いずれも「オブジェクトの集合を返す」という同じ概念)は、
  1つのツールにパラメータで分岐させて統合する。
- 一方、**操作の意味が異なるものは統合しない**。パラメータの形が大きく異なる場合
  (例: プロジェクトの保存/読み込み/新規作成/ファイル出力)、無理に1ツールへ
  まとめるとパラメータの意味が曖昧になり、却って使いにくくなる。
- **補助的な情報取得は、可能なら本体の操作に畳み込む**。例えば「有効な値の一覧」は
  独立ツールにするより、誤った値を渡したときのエラーメッセージに含める方が
  ツール数を増やさずに済む場合がある。
- 新しいカテゴリを実装する際は、SDK関数を1つずつ機械的にツール化する前に、
  「これらの関数はエージェントにとって1つの概念か、複数の概念か」を先に検討する。

## 次の一手

カテゴリA・B・D・Fの基本機能は実装済み(詳細は各design docのステータスを参照)。
ツール設計の最適化(上記原則に基づく統合)を実施済み:
`find_object`/`list_objects`/`get_selected_objects` → `aviutl2_query_objects`(scope切替)に統合、
`list_output_plugins`は独立ツールを廃し`output_file`のエラー応答に統合。

カット編集(`aviutl2_split_clip`)を実装済み。SDKの区間操作API
(`create_object_section`等)はAviUtl(1)由来の「パラメータ補間の区切り」機能であり、
クリップの物理分割には使えないと判明したため、代わりに
[削除→前半/後半を同じ内容で再作成→動画/音声は再生位置をオフセット]という
複合操作で実現した([02_EDIT_OPERATIONS.md](design/02_EDIT_OPERATIONS.md)参照)。

エフェクトの追加・削除・一覧(`aviutl2_create_effect`/`aviutl2_delete_effect`/
`aviutl2_list_object_effects`)を実装済み。`effect_id`は`object_id`と同じ
解決戦略(全件走査してIDが一致するものを探す)を踏襲した。実機検証で、
出力系エフェクト(「標準描画」等)も削除できてしまうことが判明し
(クラッシュはしないが描画が消える)、ツールの説明文に注意書きを追加した。
